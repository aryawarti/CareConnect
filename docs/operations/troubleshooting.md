# Troubleshooting

Living document — every real issue hit during development gets an entry: symptom → cause → fix. Placeholder sections below are pre-seeded because these are the predictable failure classes for this stack.

## Infrastructure
- **Services stuck `(unhealthy)`, `Started ... in 200+ seconds` in the logs, and some containers never created at all** → resource starvation, not a code fault. Ten JVMs + Postgres + Kafka on a laptop will crawl if Docker Desktop has little memory, healthchecks then time out, and Compose *aborts the remaining services* when a dependency fails (hence missing containers). Fixes applied: `-XX:TieredStopAtLevel=1` (C1-only JIT — far faster startup), `-XX:MaxRAMPercentage=40` and per-container `mem_limit`, plus 150–210s healthcheck `start_period`. Also raise Docker Desktop memory to **8 GB+** (Settings → Resources). On a constrained machine, run infra in Docker and only the service you're editing on the host.
- **Windows/WSL2: Docker Desktop silently caps itself at ~50% of host RAM** (e.g. 3.65 GB on a 7.7 GB machine) regardless of the Settings → Resources slider, and the whole platform profile crawls or individual services never finish starting even though nothing crashes. Fix: create/edit `%USERPROFILE%\.wslconfig` with `[wsl2]` / `memory=<N>MB` (leave enough for Windows itself — e.g. 5.5 GB on a 7.7 GB host, not the full "8 GB+" recommendation above if the host doesn't have it to give), then `wsl --shutdown` and restart Docker Desktop for it to take effect. Diagnostic tell: `docker info --format '{{.MemTotal}}'` reports far less than expected, and `docker stats` shows containers well under their `mem_limit` yet everything is still glacially slow.
- **After `cp .env.example .env` on a machine that already has a running stack: every business service crashes on startup with `FATAL: password authentication failed for user "careconnect"`** → Postgres only applies `POSTGRES_PASSWORD` when it *initializes* an empty data directory; on a pre-existing `postgres-data` volume the real password is whatever was set the first time, which — if no `.env` existed yet — was the inline default in `docker-compose.yml` (`careconnect`), not the placeholder in `.env.example` (`change-me-locally`). Copying the example file over an already-initialized environment introduces a mismatch between what the *services* send and what Postgres actually has. Fix: set `.env`'s `POSTGRES_PASSWORD` to match the value the volume was actually initialized with (don't just trust the example file), or if starting genuinely fresh, `docker compose down -v` first so the new password takes effect on a clean volume.
- **Docker image build fails with `Temporary failure in name resolution` for repo.maven.apache.org** → Docker Desktop's internal DNS broke (common after sleep/VPN/network switch). Restart Docker Desktop. Root fix applied: Dockerfiles are now runtime-only — jars are built on the host (`mvn -q package -DskipTests` in `backend/`) and copied in, so image builds are seconds and never resolve dependencies.
- **Windows: `error during connect: ... //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified`** → Docker Desktop isn't running. Start it, wait for "Engine running", retry. Note: Phase 1 platform services need no containers at all — they can run via `mvn spring-boot:run` directly.
- **Kafka `localhost:9092` unreachable from a service in Compose** → services inside the network must use `kafka:19092` (internal listener); `localhost:9092` is the host-machine listener. See listener config in `docker-compose.yml`.
- **Postgres init scripts didn't run** → they only run on an empty volume: `docker compose down -v && docker compose up -d`.

## Platform
- **Every authenticated request 401s (public routes fine); the SPA bounces to /login on protected pages** → the gateway was stripping its own identity headers. `default-filters: RemoveRequestHeader=X-User-Id` are *route* filters, which run **after** global filters — so `JwtAuthGlobalFilter` set the headers and the route filter deleted them; services saw an anonymous request. Fix: strip inbound headers inside the JWT filter itself (public paths: remove; authenticated: `set()` overwrites), and never add RemoveRequestHeader default-filters for these. Diagnostic tell: gateway logs show the route matched, the service log shows a 401 with no `X-User-Id`.
- **User is bounced to /login when navigating after the access token expires** → the SPA fired two refreshes in parallel (two components each hitting a 401). The backend rotates refresh tokens and treats a replayed one as theft, so it revoked the whole session — correct backend behaviour, client bug. Fix: `AuthService.refresh()` is single-flight (shared in-flight observable); concurrent 401s await one refresh. Diagnostic tell: a 401 on `/api/auth/refresh` in the network tab, and `revoked refresh token replayed` in identity-service logs.
- **Every GET works but every POST returns 403 with an empty body** → gateway CORS rejection, not authentication. Browsers attach an `Origin` header to same-origin POST/PUT/DELETE (but not GET); Spring Cloud Gateway's CORS filter blocks unlisted origins with a bare 403 *before* routing. Fix: list every SPA origin in `globalcors` (`4200` ng serve, `4300` nginx container). Hit when the containerized frontend was introduced.
- **Container healthcheck fails / `dependency <service> failed to start`, while the service log shows only `TimedSupervisorTask timed out`** → the app is fine; the *health signal* was wrong. Two causes, both fixed: (1) `eureka.client.registry-fetch-interval-seconds` doubles as the Eureka cache-refresh **task timeout** — our 5s dev value guaranteed timeouts on a cold, loaded machine (now 10s); (2) healthchecks hit `/actuator/health`, whose aggregate includes the discovery indicator, so a flaky registry marked healthy instances unhealthy and cascaded. Healthchecks now use `/actuator/health/readiness` (readinessState only), with 60–90s `start_period` for cold JVM starts.
- **Gateway returns 503 with a correlation ID for an `lb://` route** → the gateway is fine; Eureka has no instance for the target. Check http://localhost:8761 — is the service registered? Two causes seen: (1) the target service has no Eureka client / registration disabled — this bit us in Phase 1 when the demo route targeted config-server before it registered anywhere (fixed by adding the Eureka client to config-server); (2) propagation lag — instance registered <30s ago; dev profile now uses 5s fetch/cache intervals, so waiting ~10s suffices.
- **Service not visible in Eureka** → check `eureka.client.service-url.defaultZone`, and that config-server was up before the service started.
- **Gateway 503 for a registered service** → registry propagation lag (~30s default); reduce lease intervals in dev profile.
- **`No servers available for service: <x>` / `No instances found after removing previously used service instance`, appearing for a service that was definitely up**, especially right after redeploying several *other* services back-to-back → discovery-server itself got starved by the redeploy burst (`ReplicationTaskProcessor: socket read timeout... some eureka node occupied all the cpu time` in its logs) and evicted leases for services that missed a heartbeat window, not just the ones being redeployed. Self-heals within the next registration cycle (services re-register automatically) — check `curl localhost:8761/eureka/apps` for the current registered-app count before assuming a real outage. If it recurs constantly, redeploy services one at a time with a beat in between rather than as a batch, and avoid hammering the gateway with your own test traffic while it's recovering (that adds to the load causing the problem).
- **A request/response that just worked from the same shell inexplicably returns an empty token or `HTTP 000`/`503` a command or two later, with no code change in between** → transient host/network flakiness under sustained load (long session, many rebuilds), not a backend bug. Isolate each `curl` into its own command (don't chain login + authenticated-call in one script) so a hiccup in one doesn't cascade into a false "auth is broken" signal, and retry once before investigating further.

## Build & tests
- **500 with `Name for argument of type [...] not specified, and parameter name information not available via reflection`** → Spring 6.1+ needs `-parameters` at compile time for `@RequestParam`/`@PathVariable` name resolution. `spring-boot-starter-parent` sets it silently; a custom parent must configure `maven-compiler-plugin` with `<parameters>true</parameters>`. Second "starter-parent invisible favor" found (first: version-property overrides).
- **Anonymous request returns 403 instead of 401** → no `AuthenticationEntryPoint` configured; Spring falls back to `Http403ForbiddenEntryPoint`. Every service's `SecurityConfig` sets an explicit 401 problem-JSON entry point.
- **Test logs show `Fetching config from server at : http://localhost:8888`** → tests were reaching the *live* config-server because `spring.config.import` in the main `application.yml` applies to test contexts too. Fix: a `src/test/resources/application.yml` (shadows the main one) with no config import — tests must be hermetic. Every service copies this pattern.
- **`@WebMvcTest` fails with `JPA metamodel must not be empty`** → `@EnableJpaAuditing` (or any JPA-touching annotation) sits on the application class, dragging JPA into slice contexts that exclude it. Fix: move it to a dedicated `@Configuration` (`JpaAuditingConfig`) — slices don't scan plain configuration classes. Hit in Phase 2.
- **`Mockito cannot mock this class` with a JVM newline in the report (e.g. Java 25)** → the JDK is newer than the Byte Buddy release bundled by Spring Boot. Fixed in the parent pom: `byte-buddy.version` override + `-Dnet.bytebuddy.experimental=true` in surefire. Bytecode still targets Java 21 (`maven.compiler.release`), so any JDK 21+ can build.
- **`Could not find a valid Docker environment` in *IntegrationTest** → Testcontainers needs Docker Desktop running. The test is annotated `disabledWithoutDocker = true`, so it skips instead of failing — run with Docker up to execute it for real.
